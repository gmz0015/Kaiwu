# 公开仓库提交与推送审查

仓库为 [gmz0015/Kaiwu](https://github.com/gmz0015/Kaiwu)，可见性为公开。提交和推送前必须执行本清单；规范权威定义见 [CONTRIBUTING](../CONTRIBUTING.md)。用户授权某次推送不免除审查，也不代表自动授权后续推送、合并或发布。

## 提交前：审查实际暂存内容

1. 查看 `git status --short` 和 `git diff --cached --stat`；确认只有本次任务授权范围内的文件，审阅 `git diff --cached` 完整补丁，包括新增文件、删除、符号链接和文件模式。
2. 检查凭证与配置：Token、API Key、私钥、签名证书、描述文件、Cookie、订阅链接、代理 Secret、真实云容器或内部地址。真实值不进入源码、测试、示例、日志、截图和文档；测试使用明确的虚构值。
3. 检查个人与内部信息：用户目录、邮箱、设备标识、真实网络配置、内部服务、客户材料、私有项目内容。通用示例用相对路径、example.com、loopback 或保留的测试地址。
4. 检查文件范围：构建缓存、应用包、归档、日志、用户 Xcode 配置及本地签名配置不得提交。`.gitignore` 仅约束未跟踪文件；通过 `git diff --cached` 和 `git ls-files` 确认最终范围，不能用 `git add -f` 绕过审查。
5. 检查来源与权限：保留 [MIT 许可证](../LICENSE) 和合法的第三方声明；不复制未获授权的源码、二进制或资料。新依赖、CI、下载执行、权限、网络修改与数据导出需要专项审阅。
6. 核对提交者身份；避免将工作邮箱或未获授权的个人信息写入 commit。推荐经 GitHub 账号核实的 noreply 邮箱，仅修改本仓库配置。
7. 按 [验证矩阵](TESTING.md) 完成相关检查，再审阅最终暂存内容。提交只包含已审查的内容。

## 推送前：审查将公开的整个范围

1. `git remote -v` 核实目标为本仓库；获取远端状态，确认目标分支。普通任务推送任务分支并走 PR，不直推 main、不强推。
2. 已有上游分支时检查 `@{upstream}..HEAD`；首次推送任务分支时检查 `origin/main..HEAD`。基线必须来自刚核实的远端状态，不能假定 `HEAD~1` 就是全部范围。
3. 查看该范围的提交列表、每个提交的完整补丁、最终 diff 以及作者/提交者信息。秘密即使在后续提交中删除，仍可能留在早期提交里；文件名和提交说明也属于公开内容。
4. 所有发现完成处理后再推送；推送后核对远端提交 SHA，检查 PR 与 CI 的实际状态。创建了工作流不等于 CI 已通过。

## 发现问题时

- 审查输出只记录类别与位置，不回显完整秘密或敏感原文。不要把带秘密的审查日志上传为 CI artifact 或粘贴到公开 issue/PR。
- 尚未提交的秘密先移出暂存范围，并改为占位示例；已进入本地未推送提交的秘密必须在推送前从这些提交中清除，不能仅追加删除提交。
- 已公开的秘密应先撤销或轮换，再协调历史清理；不得擅自强推或重写他人历史。新发现授权不明的材料先停止其发布并明确处理方式。
- 本仓库的 `make lint` 不提供完整秘密检测。模式扫描只是辅助，无法证明不存在任意秘密、个人信息或许可问题，必须结合人工审阅。

## 记录格式

每次提交/PR记录以下内容；初次初始化记录见 [首次公开审查](reviews/2026-10-12-initial-public-review.md)。

- 范围：基线、目标分支、文件/提交范围。
- 发现与处理：只写类型、位置、处理结果，不包含秘密原文。
- 验证：实际命令、结果、环境；区分本地检查和远端 CI。
- 限制：未验证项或仍待处理的问题；存在泄露或授权阻塞时不得推送。
